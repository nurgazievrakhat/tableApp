# tableEasyApp — проект приложения

Настольное приложение для Windows: поиск товаров и сравнение цен по набору
прайс-листов поставщиков в форматах `.xlsx` / `.xls`.

## 1. Ключевое решение

**Файлы не читаются в момент поиска.** Прайс импортируется один раз, разбирается,
нормализуется и складывается в локальную SQLite с полнотекстовым индексом FTS5.
Поиск идёт по базе.

Почему не «искать по файлам напрямую»: открытие xlsx — это распаковка zip плюс
разбор XML, порядка секунды на файл среднего размера. На 30–50 прайсах каждый
запрос превращался бы в минутное ожидание. С базой поиск по миллиону позиций —
десятки миллисекунд.

Файлы при этом остаются источником правды: храним путь, хеш и mtime. Если файл
на диске изменился — приложение предлагает переимпорт.

```
  xlsx/xls ──▶ парсер ──▶ детект шапки ──▶ маппинг колонок ──▶ нормализация ──▶ SQLite + FTS5
                                                 ▲                                    │
                                        профиль поставщика                            ▼
                                       (сохраняется, при повторном            поиск / сравнение /
                                        импорте применяется сам)               история / экспорт
```

## 2. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Оболочка | Electron | Разработка и отладка полностью на macOS, цель — Windows |
| UI | React + TypeScript | Виртуализированный грид для десятков тысяч строк |
| Оформление | обычный CSS с токенами | Своя шкала отступов и типографики, без зависимостей |
| Парсинг | SheetJS (`xlsx`) | Единственная зрелая JS-библиотека, читающая и `.xlsx`, и старый `.xls` |
| Хранилище | SQLite (`better-sqlite3`) + FTS5 | Синхронный API, быстрый, встраивается в дистрибутив |
| Слежение за папками | chokidar | `awaitWriteFinish` — без него файл читается на середине копирования |
| Сборка `.exe` | electron-builder на GitHub Actions (windows-latest) | Собирать NSIS-инсталлятор с Mac ненадёжно |

Режим работы: **один ПК, одна локальная база**. Файл базы — в
`%APPDATA%/tableEasyApp/data.db`.

## 3. Процессы

Electron даёт три исполнительных контекста, и разделение между ними здесь
принципиально, иначе интерфейс будет замерзать на импорте.

- **main** — жизненный цикл окна, диалоги выбора файлов, владение соединением с SQLite.
- **worker** (`utilityProcess` или `worker_threads`) — разбор xlsx. Файл на 100k
  строк парсится единицы секунд и полностью блокирует поток, поэтому он уезжает
  из main. Прогресс шлём в UI сообщениями.
- **renderer** — React. К базе напрямую не ходит, только через IPC (`contextIsolation: true`,
  `nodeIntegration: false`).

## 4. Схема данных

```sql
CREATE TABLE suppliers (
  id    INTEGER PRIMARY KEY,
  name  TEXT NOT NULL UNIQUE,
  note  TEXT
);

-- Как читать конкретный прайс. Ключевая таблица для «импорт в один клик».
CREATE TABLE mappings (
  id              INTEGER PRIMARY KEY,
  supplier_id     INTEGER REFERENCES suppliers(id),
  signature       TEXT,               -- хеш строки заголовков → авто-подбор профиля
  header_row      INTEGER NOT NULL,
  data_start_row  INTEGER,
  columns_json    TEXT NOT NULL,      -- {"name":2,"price":5,"article":1,"unit":6}
  currency        TEXT DEFAULT 'RUB',
  price_multiplier REAL DEFAULT 1.0   -- если прайс в тысячах или с наценкой
);

CREATE TABLE files (
  id          INTEGER PRIMARY KEY,
  supplier_id INTEGER NOT NULL REFERENCES suppliers(id),
  path        TEXT NOT NULL,
  sheet       TEXT NOT NULL,
  file_hash   TEXT,                   -- sha1, чтобы не импортировать то же дважды
  mtime       INTEGER,
  mapping_id  INTEGER REFERENCES mappings(id),
  UNIQUE(path, sheet)
);

CREATE TABLE imports (
  id           INTEGER PRIMARY KEY,
  file_id      INTEGER NOT NULL REFERENCES files(id),
  imported_at  INTEGER NOT NULL,
  price_date   INTEGER,               -- дата самого прайса, см. §9
  rows_total   INTEGER,
  rows_ok      INTEGER,
  rows_skipped INTEGER
);

-- Актуальная позиция прайса: одна строка на товар поставщика
CREATE TABLE items (
  id             INTEGER PRIMARY KEY,
  supplier_id    INTEGER NOT NULL REFERENCES suppliers(id),
  file_id        INTEGER NOT NULL REFERENCES files(id),
  item_key       TEXT NOT NULL,       -- стабильный ключ внутри поставщика, см. §7
  name           TEXT NOT NULL,
  name_norm      TEXT NOT NULL,
  article        TEXT,
  article_norm   TEXT,
  price          REAL,                -- ровно как в прайсе
  currency       TEXT,
  promo_raw      TEXT,                -- исходный текст колонки «Акция»
  promo_pct      REAL,                -- безусловная скидка, %
  promo_from     INTEGER,             -- период действия
  promo_to       INTEGER,
  bulk_pct       REAL,                -- доп. скидка от количества, %
  bulk_min_qty   INTEGER,             -- «при покупке от N уп»
  unit           TEXT,
  unit_norm      TEXT,                -- упак/уп/упаковка -> уп
  stock          TEXT,
  category       TEXT,                -- подхвачена из строки-разделителя
  row_no         INTEGER,             -- «показать, откуда взято»
  extra_json     TEXT,                -- все прочие колонки прайса, для показа
  extra_text     TEXT,                -- те же значения плоским текстом, только для FTS
  product_id     INTEGER REFERENCES products(id),
  last_import_id INTEGER REFERENCES imports(id),
  is_active      INTEGER DEFAULT 1,   -- пропала из последнего импорта → 0
  UNIQUE(supplier_id, item_key)
);

-- История цен: запись только при фактическом изменении
CREATE TABLE price_history (
  item_id    INTEGER NOT NULL REFERENCES items(id),
  price      REAL,
  currency   TEXT,
  changed_at INTEGER NOT NULL,
  import_id  INTEGER REFERENCES imports(id),
  PRIMARY KEY (item_id, changed_at)
);

-- Канонический товар: склеивает позиции разных поставщиков
CREATE TABLE products (
  id         INTEGER PRIMARY KEY,
  title      TEXT NOT NULL,
  match_key  TEXT,                    -- норм. артикул или норм. название
  created_by TEXT                     -- 'auto' | 'manual'
);

CREATE VIRTUAL TABLE items_fts USING fts5(
  name_norm, article_norm, extra_text,
  content='items', content_rowid='id',
  tokenize='unicode61 remove_diacritics 2'
);
```

`extra_json` закрывает требование «возможно, ещё какие-то данные о продуктах»:
любые колонки сверх базовых сохраняются и показываются в карточке позиции, не
требуя миграции схемы.

Пара `extra_json` / `extra_text` разделена не для удобства, а по требованию FTS5.
При `content='items'` индекс сопоставляет свои колонки с колонками таблицы **по
имени**, поэтому колонка `extra_text` обязана существовать в `items` — иначе
падает всё, что обращается к содержимому (включая `count(*)` и каскадное
удаление), хотя сам поиск при этом продолжает работать и баг выглядит
безобидным. Заодно разделение полезно по сути: в индекс попадает человеческий
текст, а не JSON со скобками и ключами.

### Резервные копии

Вся работа приложения лежит в одном файле `data.db`, и история цен —
единственный экземпляр данных, которые заново не собрать: прошлогодний прайс у
поставщика уже не попросишь. Поэтому копия снимается сама при запуске —
обязательно перед миграцией и не чаще раза в сутки, — в `userData/backups`,
последние семь.

Копия делается через `VACUUM INTO`, а не копированием файла. При WAL часть
свежих изменений лежит в отдельном журнале, и `copyFile` дал бы копию,
отставшую от базы или несогласованную. `VACUUM INTO` пишет цельный снимок на
момент запроса и заодно сжимает его — на реальной базе 13 МБ превращаются в
6,5 МБ.

Секунды в имени файла (`data-2026-09-05-191824.db`) нужны не для чтения, а
чтобы имена сортировались по времени как строки: хвост `-2` при совпадении
встал бы перед точкой и выглядел старше копии без хвоста, а по этому порядку
выбирается и последняя копия, и то, что вытесняется из ротации.

Возврат к копии — отдельная операция с двумя условиями. Первое: копия
проверяется на открываемость **до** того, как закрывается рабочая база, иначе
отказ на повреждённом файле оставит приложение вообще без базы. Второе: файл
сначала кладётся рядом и переименовывается на место, поэтому нехватка места
оборвёт копирование во временный файл, а рабочая база останется целой. Журналы
`-wal` и `-shm` после подмены удаляются: они относятся к прежнему файлу, и
SQLite попытался бы накатить на новый чужие изменения. Нынешнее состояние перед
возвратом тоже уходит в копию, а приложение перезапускается — часть данных уже
прочитана в память окна и после подмены была бы неправдой.

## 5. Конвейер импорта

Прайс-листы поставщиков — один из самых грязных форматов данных, которые
встречаются. Импорт должен переживать всё нижеперечисленное.

**Шаг 1. Детект строки заголовков.** Шапка почти никогда не в первой строке:
сверху логотип, контакты, реквизиты, условия работы. В прайсе Неман-Фарм
преамбула занимает **262 строки** и содержит **три акционные таблицы** со своими
заголовками (`Наименование|Скидка|Поставщик`, `Продукт|Цена ДО|Цена ПОСЛЕ`,
`№|Продукт|При покупке, уп`). Каждая из них выглядит как прайс и ни одна им не является.

Поэтому правило «первая строка, похожая на заголовок» — неверное. Сканируем **весь
лист**, собираем всех кандидатов, и выбираем того, **под кем самый длинный
непрерывный блок однотипных строк с числовой ценой**. Настоящий прайс — это
тысячи строк, ловушки — десятки. Дополнительные признаки веса: наличие колонки
цены, колонки единиц измерения, сквозной нумерации в первой колонке.

Пользователь видит найденный вариант и список отвергнутых кандидатов, может переключиться.

**Шаг 2. Классификация колонок** по словарю синонимов:

| Поле | Варианты в реальных прайсах |
|---|---|
| `name` | Наименование, Товар, Название, Номенклатура, Наименование товара, Описание |
| `price` | Цена, Стоимость, Цена руб, Цена с НДС, Розница, Опт, Прайс |
| `article` | Артикул, Код, Код товара, Арт., SKU, Кат. номер |
| `unit` | Ед., Ед. изм., Единица, шт/м/кг |
| `stock` | Остаток, Наличие, Кол-во, Склад |

Совпадение — по нормализованному заголовку с допуском на опечатки. Если в файле
несколько ценовых колонок (розница и опт) — спрашиваем, какую брать основной;
вторая уезжает в `extra_json`.

**Шаг 3. Подтверждение маппинга.** Экран с превью первых 30 строк и
выпадающими списками над колонками. Пользователь правит, что не угадалось, и
сохраняет как профиль поставщика. Профиль привязывается к `signature` — хешу
строки заголовков. В следующий раз тот же прайс импортируется одной кнопкой,
без вопросов.

**Шаг 4. Разбор строк.** Что должно быть обработано:

- строки-категории (`ЛЕКАРСТВЕННЫЕ ТРАВЫ`, `3. Биологически активная добавка`) —
  не товар; запоминаются и проставляются в `category` следующим позициям.
  Правило «есть название, нет цены → категория» **неверно**: в прайсе Неман-Фарм
  строка 365 (`АЛКСОИД В ПОЛИМЕР 1*2,5мл амп`) — реальный товар без цены.
  Рабочее правило: категория — это строка, где **пусты одновременно № п/п,
  цена, единица измерения и производитель**;
- объединённые ячейки — SheetJS отдаёт значение только в левой верхней, остальные
  пустые; протягиваем значение вниз/вправо по диапазону `!merges`;
- **цена текстом.** Это не редкий случай, а норма: в прайсе Фармамира *все* 2703
  цены — текстовые строки вида `1417,92`, а № п/п — текст `2 700` с пробелом-
  разделителем разрядов. В прайсе Неман-Фарм те же цены — нормальные числа.
  Парсер обязан принимать оба варианта: снятие пробелов (включая `\xa0`), запятая
  как десятичный разделитель, отбрасывание `₽/руб/сом/KGS`. Непарсящееся
  (`от 1200`, `договорная`, `—`) кладём в `extra_json` и оставляем `price = NULL`;
- пустые строки, строки с примечаниями, дубли шапки в середине листа — отбрасываем;
- несколько листов в книге — каждый лист импортируется как отдельная связка
  `files` + `mapping`, лишние («Инструкция», «Условия») пользователь снимает галочкой.

**Шаг 4б. Ловушки, найденные на прайсах шести поставщиков.**

*Кодировка.* BIFF хранит строки в кодировке из записи CODEPAGE. Без таблицы
кодовых страниц SheetJS читает их как Latin-1, и «ОсОО "БИМЕД Фарм"»
превращается в «ÎñÎÎ "ÁÈÌÅÄ Ôàðì"» — детектор после такого не находит вообще
ничего. Из восьми прайсов три оказались в CP1251. Лечится одной строкой
`XLSX.set_cptable(cptable)`, но без неё файл выглядит нечитаемым.

*Повтор шапки.* Поставщики дублируют строку заголовков через каждые несколько
десятков строк — чтобы она была видна при прокрутке и на печати. Правило
«блок обрывается на следующей шапке» резало из-за этого одну таблицу на куски:
у Бимед-Фарма терялись 56 позиций из 3055, а сама повторная шапка приезжала в
базу товаром с названием «Наименование». Повтор **той же** шапки — служебная
строка внутри таблицы, а не начало новой.

Сравнивать шапки целиком нельзя: у «Лектос» одна и та же шапка в разных секциях
идёт то с колонкой «Уп», то без неё. Значимо совпадение тех колонок, которые
размечены, — это и есть структура таблицы.

*Пустые строки не обрывают таблицу.* Посреди прайса «Лектос» стоят 19 пустых
строк подряд. По прежнему правилу (не более 12 «не-товарных» строк) блок
обрывался на них, и терялись 763 позиции из 1320 — больше половины. Пустая
строка ничего не говорит о том, что таблица кончилась; в счёт разрыва идут
только строки с содержимым.

*«Наличный» — это цена, а не остаток.* Правило `/^(остат|налич)/` ловило и
«наличие» (сколько на складе), и «наличный» (форма оплаты). У «Прима
Интернэшнл» весь прайс держится на колонке «Наличный», и приложение осталось
бы вовсе без цен.

**Шаг 4в. Сверка разметки с данными.** Заголовок может врать. В прайсе
«Медлайф» колонка подписана «ПРОИЗВОДИТЕЛЬ», а под ней даты; соседняя подписана
«СРОК ГОДНОСТИ», а под ней названия заводов. Поверив подписям, приложение молча
теряет все 3087 сроков годности.

Поэтому после разметки берётся выборка до 200 строк и проверяется, похожи ли
значения на ожидаемые: под ценой числа, под сроком даты, под производителем
текст. Если совпадений меньше 40%, колонка помечается в окне разметки, и
подсказывается та, где нужные значения лежат на самом деле. Приложение при этом
ничего не переставляет само — решает человек.

**Шаг 5. Запись.** Одна транзакция на файл, подготовленные операторы. На
реальных данных FTS-триггеры оказались недорогими: 5655 позиций пишутся за
220мс вместе с индексом, 2703 — за 66мс. Отключать триггеры на время вставки с
последующим `rebuild` пока незачем; если появится прайс на сотню тысяч строк,
это первое место, куда стоит посмотреть.

Гашение исчезнувших позиций идёт **по поставщику, а не по файлу**: прайс
следующей недели приходит новым файлом, но каталог у поставщика тот же, и
позиции ключуются именно по нему. Область гашения обязана совпадать с ключом,
иначе пропавшие товары остаются «активными» навсегда.

## 6. Нормализация и поиск

Пользователь наберёт `ввг 3*2.5`, а в таблице будет `Кабель ВВГнг(А)-LS 3х2,5`.
Без нормализации поиск бесполезен.

**Правила нормализации** (применяются и к данным при импорте, и к поисковому запросу):

1. нижний регистр, `ё` → `е`;
2. гомоглифы кириллица/латиница (`а e o p c y x k b h m t`) приводятся к одному
   алфавиту — иначе `ВВГ` латиницей и кириллицей будут разными строками;
3. `×`, `*`, `х`, `x` между числами → единый символ `x`;
4. запятая внутри числа → точка: `3,5` → `3.5`;
5. пробелы вокруг разделителей схлопываются: `3 х 2.5` → `3x2.5`;
6. схлопывание повторяющихся пробелов;
7. число склеивается с единицей измерения: `100 мкг` → `100мкг`. В прайсах
   пишут слитно, а пользователь наберёт через пробел — без склейки запрос
   распадался на два токена, и одинокого `мкг` в индексе не находилось.
   Проверено: `селен 100 мкг` давал ноль результатов.

Артикул нормализуется жёстче: всё кроме букв и цифр удаляется, верхний регистр.

**Осторожно с `\b` в регулярных выражениях.** В JavaScript граница слова
определена только по ASCII, поэтому после кириллицы она молча не срабатывает:
`/^цена\b/` не находит «цена за ед товара». На этом уже один раз потерялась
колонка цены в прайсе Фармамира — детект отработал, а поле осталось пустым, и
ошибка выглядела как проблема словаря. Границы слова писать как `(?![а-яa-z])`.
По той же причине символы вроде `№` нужно явно оставлять в наборе разрешённых:
иначе «№ п/п» превращается в «п п».
`ВВГ-3х2.5` и `ВВГ 3Х2,5` дают один `article_norm`.

**Ранжирование результатов:**

1. точное совпадение по `article_norm` — всегда наверх;

   Артикул при этом требует отдельной ветки запроса. «D-001» режется
   токенизатором на `d` и `001`, а в индексе артикул лежит слитно — `d001`.
   Стороны не сходятся, и вместо нужной позиции выдача забивается всем, где
   есть слово на «d» и число на «001». Поэтому для запроса, похожего на код
   (без пробелов и с цифрой), к выражению добавляется альтернатива
   `... OR "d001"*`.

2. FTS5-запрос из токенов с префиксным матчем (`ввг* AND 3x2.5*`), сортировка по `bm25()`;
3. если не нашлось **ничего** — исправление опечаток и повтор запроса.

**Опечатки правятся по словарю самих прайсов, а не по словарю языка.** «ВВГнг»,
«АЭРТАЛ», «СОЛГАР» ни в одном общем словаре не встретятся, зато в товарных
названиях это самые частые слова. Словарь берётся из `fts5vocab` поверх
поискового индекса — отдельного хранилища не требует.

Правится только слово, которого в прайсах нет вовсе; найденное префиксно не
трогается, иначе сокращение «церебр» превратилось бы в «церебролизин» и сузило
выдачу. Расстояние Левенштейна с бюджетом по длине: до 3 букв не правим совсем,
до 5 — одна замена, дальше — две. При равном расстоянии побеждает более частое
слово. Если после правки по-прежнему ничего нет, возвращается пустой результат
с исходным запросом — чушь остаётся чушью.

От триграммного добора отказались: он даёт подстроку, а не терпимость к
опечаткам. У «аэртл» и «аэртал» общих триграмм только две из трёх, и FTS с
триграммным токенизатором такую пару не свяжет.

## 7. Сопоставление товаров между поставщиками

Нужно для сравнения цен, и это самая рискованная часть приложения.

Стабильный ключ позиции **внутри** поставщика (`items.item_key`): нормализованный
артикул, если он есть, иначе хеш от `name_norm`. Номер строки для этого не годится
— поставщик вставит три позиции в середину, и вся история цен разъедется.

Срок годности в ключ намеренно **не** входит, хотя и различает часть дублей: он
меняется с каждой поставкой, и позиция при переимпорте выглядела бы новой,
обрывая историю цен.

Но в прайсах есть строки-близнецы: у Неман-Фарма «ГЕРБИОН ПЛЮЩ 150мл сироп»
идёт дважды — за 390 и за 153, разные партии с разным сроком. Это не мусор, обе
строки нужны. Столкнувшиеся ключи разводятся суффиксом, и порядок суффиксов
задаётся **ценой, а не позицией в файле**: иначе перестановка строк поставщиком
приписала бы одной партии историю другой. Таких позиций единицы — 10 из 5655 у
Неман-Фарма, 12 из 2703 у Фармамира.

Осторожно с `UNIQUE(supplier_id, item_key)`: в обоих прайсах есть дубли названий
(5 пар у Неман-Фарм, 6 у Фармамира). Часть — соседние строки (`ГЕРБИОН ПЛЮЩ 150мл`
в строках 927 и 928), часть — один товар в двух категориях (`ЗОЛОМАКС 1мг №30`
в строках 3112 и 5773, потому что блок «Сильнодействующие» в файле встречается
дважды). Импорт не должен падать: при коллизии оставляем строку с минимальной
ценой, остальные складываем в `extra_json` как `duplicate_rows` и показываем
в логе импорта.

**В присланных прайсах колонки артикула нет ни у одного поставщика.** Есть только
сквозная нумерация `№ п/п`, которая меняется при каждом обновлении файла и ключом
служить не может. Значит сопоставление возможно только по названию, и это
проверено на реальных данных (5655 позиций Неман-Фарм против 2703 Фармамира):

| Метод | Совпадений | Пригодность |
|---|---|---|
| Точное совпадение `name_norm` (базовая нормализация) | 511 | автосклейка безопасна |
| То же + нормализация пробелов в числах и скобочных хвостов | 520 | автосклейка безопасна |
| Бренд + дозировка + количество совпадают | +788 | **только в очередь на подтверждение** |

Улучшения нормализации, которые дали +9 и нужны обязательно: `1 158мг` → `1158мг`
(пробел-разделитель разрядов внутри числа), отброс дублирующего хвоста
`СОЛГАР (SOLGAR)`, `NATURES'S BOUNTY` → `natures bounty`, унификация `+` и `-`
в составных названиях (`МЕНТОЛ+ЭВКАЛИПТ` / `МЕНТОЛ-ЭВКАЛИПТ`).

Итоговая лестница:

1. **совпал `article_norm`** → автоматически один `product` (на будущее, если
   появится поставщик с артикулами);
2. **совпал `name_norm` точно** → автоматически один `product`;
3. **совпали бренд + дозировка + количество, но не строка целиком** → в очередь
   на подтверждение, НЕ склеиваем;
4. **ручная склейка** пользователем → сохраняется навсегда и применяется при
   следующих импортах.

Почему пункт 3 не автоматизируется — это измерено, а не предположение. Среди пар с
высоким сходством:

```
0.92  АЗИТРОМИЦИН 500мг №3 табл САНДОЗ   ≠  АЗИТРОМИЦИН 500МГ №3 ТАБЛ АДЖИО
0.85  КОЭНЗИМ Q10 100мг №30 капс СОЛГАР  ≠  КОЭНЗИМ Q-10 60МГ №30 КАПС СОЛГАР
      МУЛЬТИ ВУМЕН №30 табл 4HEALTH      ≠  МУЛЬТИ-ONE МУЛЬТИВИТ №30 ТАБЛ СОЛГАР
      АДЖИСЕПТ №100 леденцы КЛАССИЧЕСКИЙ ≠  АДЖИСЕПТ №100 ПАСТ МЕД-ЛИМОН
0.83  МАСЛО КРИЛЯ 500мг №30 капс ...     =  МАСЛО КРИЛЯ 500МГ №30 КАПС ...   ← верное
```

Самая высокая оценка сходства во всей выборке (0.92) — у **ложной** пары: разные
производители одного дженерика, разные товары, разные цены. А верная пара (масло
криля) набирает 0.83. **Порог, разделяющий верные и ложные совпадения, не
существует** — оценка сходства их не разделяет в принципе. Правило
«бренд+дозировка+количество» тоже течёт: оно игнорирует вкус и форму выпуска и
склеивает `АДЖИСЕПТ КЛАССИЧЕСКИЙ` с `АДЖИСЕПТ МЕД-ЛИМОН`, а один товар слева
матчится сразу на два справа.

Колонка производителя помочь не может: у Неман-Фарм это страна (`США`, `Индия`),
у Фармамира — завод (`SOLGAR/США`, `Psychotropics India`). Как жёсткий ключ
непригодна, но в очереди подтверждения показывается человеку — там она решает
спор за секунду.

Вывод для UI: **очередь подтверждения — обязательный экран, а не опция.** ~800
кандидатов на два прайса разобрать разом нереально, поэтому очередь ленивая:
кандидаты строятся и показываются для тех товаров, которые пользователь реально
открыл в поиске. Подтверждённое запоминается навсегда.

## 8. История цен

При переимпорте файла `items` обновляется на месте, а старое значение уходит в
`price_history` — **только если цена реально изменилась**. Полные снимки всех
строк на каждый импорт раздули бы базу на порядок без пользы.

Что это даёт: в карточке позиции — ступенчатый график и список изменений; в
результатах поиска — маркер «▲ +8%» с прошлой ценой в подсказке; отдельная
вкладка «Изменения» с отчётом за неделю, месяц, квартал или всё время, с
фильтром по направлению и поставщику.

**Тонкость восстановления «стало».** В `price_history` лежит цена, которая была
ДО изменения. Значит новая цена — это старая цена следующей записи, а для самой
последней записи — текущая цена позиции (`LEAD` по окну). Без этого весь график
и весь отчёт оказались бы сдвинуты на одно изменение.

График строится ступенькой: цена держится до следующего изменения, а не
интерполируется между точками — между двумя прайсами цена не менялась плавно.
Если все изменения пришлись на один день, шкала времени вырождается, и точки
раскладываются равномерно по порядку.

Позиции, исчезнувшие из последнего импорта, не удаляются, а помечаются
`is_active = 0`: история сохраняется, а в поиске они по умолчанию скрыты.

## 9. Автоимпорт из папки

Импорт по умолчанию автоматический, с ручным режимом как запасным.

Приложение следит за назначенными папками (`chokidar`). Появился новый или
изменившийся файл — конвейер:

```
новый файл ──▶ sha1 содержимого
                    │
                    ├─ хеш уже в базе ──▶ пропустить молча
                    │                     (закрывает «прайс (2).xlsx» — повторную загрузку)
                    │
                    └─ новый ──▶ найти строку заголовков (§5) ──▶ signature = sha1(заголовки)
                                        │
                                        ├─ signature есть в mappings ──▶ импорт автоматически,
                                        │                                уведомление «Фармамир: +12 / ~340 цен»
                                        │
                                        └─ signature неизвестна ──▶ в очередь «требуют настройки»,
                                                                    ручной маппинг один раз
```

**Определение поставщика — по сигнатуре заголовков, не по имени файла.** Имя
файла ненадёжно: `оптовый прайс 21.08.26 (2).xlsx` не содержит поставщика вовсе
(«Неман-Фарм» упомянут только внутри, в строке 4 свободным текстом), а `(2)` —
след повторного скачивания. Сигнатуры у двух присланных прайсов разные и
устойчивые:

```
Неман-Фарм  cf920709a3a4  ['№ п/п','Наименование','НДС','Акция',...]      9 колонок
Фармамир    70686b2f7d2d  ['№ п/п','Наименование','Ед. изм.','Нет скидки',...] 10 колонок
```

Риск коллизии реален: Фармамир — выгрузка 1С (лист `TDSheet`), и другой поставщик
на том же шаблоне 1С даст ту же сигнатуру. Поэтому ключ составной —
**сигнатура + маска имени файла** (`Прайс Фармамир от *.xls`). Если сигнатура
совпала, а маска нет — не угадываем, а спрашиваем, к какому поставщику отнести.

**Дата прайса берётся из файла, а не из `mtime`.** Оба поставщика её проставляют:
Неман — в ячейку A1 (`21,08.2026`, с опечаткой-запятой, парсер должен быть
терпимым), Фармамир — в F1 (`18.08.2026`); и оба дублируют в имени файла. Это
важно для истории цен: скачанный позже старый прайс не должен выглядеть свежее
актуального. Приоритет — ячейка, затем имя файла, затем `mtime`.

Ручной импорт остаётся всегда доступен: кнопка «Добавить файл».
Очередь «требуют разметки» — тот же экран маппинга, просто заполненный заранее.

**Пауза на стабилизацию записи обязательна.** Прайс попадает в папку копированием
или скачиванием, и без `awaitWriteFinish` разбор стартует на середине записи и
падает на битом zip. Порог — 1.5 секунды; на живой проверке файл подхватывался
примерно за две.

Файлы обрабатываются по одному через очередь: два события подряд на один и тот
же файл — обычное дело, а параллельный разбор нескольких прайсов только отнимал
бы память.

Обход папок делается и при старте приложения — иначе прайсы, положенные пока
программа была закрыта, остались бы незамеченными.

## 10. Цены, скидки и НДС

Показываем **и цену из прайса, и цену с учётом условий** — как вы и просили.

Колонка `Акция` у Неман-Фарм содержит готовый разбираемый текст. Проверено: один
regex покрывает **все 23 встречающихся варианта**, других форм нет.

```
Скидка: - 20% (10.08.2026-30.09.2026)                         → безусловная
Доп Скидка: - 29% При покупке от 3 уп (01.07.2026-31.08.2026) → от количества
```

Разбирается в `promo_pct` / `promo_from` / `promo_to` и `bulk_pct` / `bulk_min_qty`.
Исходный текст сохраняется в `promo_raw` — если regex однажды не справится с новой
формой, данные не потеряются, а строка попадёт в лог импорта.

**Эффективная цена не хранится, а вычисляется при запросе.** Скидка привязана к
периоду: цена, посчитанная на момент импорта, назавтра станет неверной. Считаем
на «сегодня» — тогда акция истекает сама, без переимпорта.

В таблице результатов три колонки:

| Цена | Со скидкой | От N уп |
|---|---|---|
| 528 | 422 *(−20% до 30.09)* | — |
| 1450 | — | 1030 *(−29% от 3 уп, до 31.08)* |

Неактивные и истёкшие акции показываются серым, а не скрываются: видно, что
скидка была и когда закончилась.

**НДС остаётся открытым вопросом, и это вопрос к поставщикам, а не к данным.**
У Фармамира прямо написано: `ЦЕНЫ УКАЗАНЫ В ВАЛЮТЕ KGS С НДС, БЕЗ УЧЕТА НСП`, а
колонка `Без НДС` пустая во всех строках. У Неман-Фарм есть колонка `НДС` со
значением `12%` у 5105 позиций из 5655 и пустая у остальных — но из файла
невозможно определить, включён этот НДС в колонку `Оптовые` или начисляется
сверх. Пока не выяснено, обе цены показываются как есть, а в профиле поставщика
заведён флаг `price_includes_vat` — когда ответ будет, это правка одной настройки,
а не переделка импорта.

## 11. Экраны

Три вкладки — **Поиск**, **Изменения**, **Прайсы**. Всё, что не является
самостоятельной работой, живёт в модальных окнах: разметка колонок, карточка
позиции, просмотр листа, состояние базы. Так навигация не разрастается по
мере появления функций.

1. **Поиск** — главный экран. Строка запроса, фильтры (поставщик, потолок цены,
   показывать ли снятые с прайса) и переключатель «Список / Сравнение цен».

   В режиме списка — одна строка на позицию: поставщик, наименование, цена,
   цена со скидкой, оптовая цена, единица, производитель, срок годности.

   В режиме сравнения — одна строка на товар: минимальная и максимальная цена,
   разброс, у кого дешевле. Строка разворачивается в предложения поставщиков с
   переплатой относительно самого дешёвого.

   **Расхождение единиц измерения помечается отдельно.** «ПАРАЦЕТАМОЛ 200МГ №10»
   идёт у одного поставщика за пластину, у другого за упаковку, и разброс в 48%
   там ничего не значит. Такие группы получают пометку «разные единицы», а
   процент показывается со знаком «≈». На текущих данных это 5 товаров из 200
   сравнимых — мало, но именно они вводили бы в заблуждение.

2. **Изменения** — что подорожало и подешевело за неделю, месяц, квартал или
   всё время, с фильтром по направлению и поставщику. Сортировка по величине
   изменения: копеечные правки не должны заслонять скачок в 127%.

3. **Прайсы** — единственный ответ на вопрос «откуда берутся данные». Здесь и
   очередь на разметку, и загруженные файлы, и папки автозагрузки.

   Очередь стоит **первой**: это единственное, что требует действия человека.

   Список файлов показывает поставщика, размер, число позиций, дату прайса и
   состояние на диске: `актуален` · `изменился` · `пересохранён` · `заменён` ·
   `файл не найден`. У каждого — «Посмотреть», «Обновить», «Удалить».

**Карточка позиции** открывается кликом по строке в любом из трёх мест. Все
колонки исходного прайса, ступенчатый график цены, список изменений и кнопка
«Показать в файле».

**Просмотр листа** — прайс целиком с виртуализацией: 5930 строк держатся без
подтормаживания, потому что в интерфейс отдаётся окно в 300 строк вокруг
видимой области, а не лист целиком. Есть переход к произвольной строке, к шапке
и к позиции, ради которой вьюер открыли. Роли размеченных колонок подписаны
**в заголовке с буквой** (`B: Наименование`, `F: Цена`), а не в строке шапки:
так они видны и когда шапка прокручена, и не ломают фиксированную высоту строки,
на которую опирается виртуализация.

**Разметка колонок** — модальное окно с одним действием «Загрузить в базу».
Раньше это были два шага, «Сохранить профиль» и отдельно «Импортировать»; их
разделение ничего не давало — колонки размечают ровно затем, чтобы загрузить
файл.

Окно устроено тремя шагами: чей прайс, что в колонках, что попадёт в базу.

*Разметка идёт прямо на фрагменте прайса.* Колонки расположены слева направо,
как в Excel, а выпадающий список стоит **над** колонкой — там, где пользователь
только что видел свои данные. Прежний вертикальный список заставлял держать в
голове соответствие «третья строка списка — третья колонка файла», хотя человек
секунду назад смотрел на ту же таблицу горизонтально.

Пустые колонки скрыты: у «Бимед Фарм» лист на 256 колонок при восьми
заполненных, у «Прима Интернэшнл» — 214 при четырёх. Показывать все — значит
утопить нужное. Кнопка «Показать все колонки» возвращает остальные.

Строка заголовков выбирается нажатием на номер строки, а не вводом числа в
поле: «строка заголовков = 263» ничего не значит для человека, который просто
видит, где в таблице начинаются названия колонок.

*Шаг «что попадёт в базу»* показывает первую позицию уже разобранной: цена как
число, срок как дата, единица приведённая. Этот блок делает ошибку очевидной
без чтения предупреждений — у «Медлайф» в строке «Производитель» стояло
`01.12.2026`, и этого достаточно, чтобы понять: колонки перепутаны.

Считает его тот же код, что и настоящий импорт: разборщики значений — чистые
функции, поэтому интерфейс берёт их напрямую, и показанное не может разойтись
с тем, что окажется в базе.

*Перепутанные подписи чинятся одним нажатием.* Если две роли указывают на
колонки друг друга, предлагается кнопка «Поменять "Срок годности" и
"Производитель"». Возиться с двумя выпадающими списками для самого частого
случая незачем.

Экспорт в xlsx не делаем — исключён из плана.

## 12. Безопасность

Приложение читает файлы, которые присылают поставщики, и держит локальную базу.
Поверхность небольшая, но у Electron есть несколько мест, где по умолчанию
опасно.

**Окно заперто на своей странице.** Preload выдаёт странице `window.api`, а он
умеет читать произвольные файлы — просмотр прайса и импорт принимают путь. Если
окно увести на внешний адрес, эти возможности достанутся ей. Поэтому:

- `setWindowOpenHandler` отклоняет любые новые окна;
- `will-navigate` пропускает только собственный адрес (`file://` в сборке,
  адрес дев-сервера в разработке);
- `will-attach-webview` запрещён;
- запросы разрешений (камера, геолокация, уведомления) отклоняются все сразу —
  приложению не нужен ни один.

**Renderer изолирован полностью.** `contextIsolation: true`, `nodeIntegration:
false` и `sandbox: true` — песочница включена, потому что preload обходится
одним модулем `electron` и Node ему не нужен. В renderer недоступны `require`,
`process` и `Buffer`, объект `window.api` заморожен.

**Содержимое прайсов рендерится как текст.** Ни `dangerouslySetInnerHTML`, ни
`innerHTML` в коде нет, поэтому названия товаров не могут стать разметкой.

**SQL везде параметризован.** В шаблоны запросов подставляются только
плейсхолдеры `?` и `@sN`, сгенерированные по длине массива, — пользовательские
данные всегда идут значениями. Токены полнотекстового поиска состоят
исключительно из букв и цифр: нормализация вырезает всё остальное до того, как
строка попадёт в выражение FTS5.

**Ссылки на `imports` удаляются мягко.** В `price_history` записано, какой
импорт изменил цену, и запись переживает переезд позиции к более свежему прайсу
— так и задумано. Но связь, объявленная без `ON DELETE`, означает `NO ACTION`:
удаление файла каскадом сносило его импорты, записи истории оставались висеть на
них, и удаление источника падало с `FOREIGN KEY constraint failed`. Правильное
поведение — `SET NULL`: факт изменения цены сохраняется, теряется лишь указание,
каким импортом оно вызвано (миграция 003).

Изменить ограничение в SQLite можно только пересборкой таблицы, поэтому миграции
идут с выключенными внешними ключами, а после них выполняется
`PRAGMA foreign_key_check` — молча включить проверку поверх испорченных данных
было бы хуже, чем упасть.

**Значения из renderer ограничены сверху.** Размер окна строк и лимит выдачи
упираются в потолок, чтобы ошибка в интерфейсе не могла вытянуть весь прайс
одним вызовом IPC.

## 13. Сборка и распространение

- Дев-цикл на macOS: `npm run dev` (Vite + Electron), полноценная отладка.
- Релиз: GitHub Actions на `windows-latest`, `electron-builder --win nsis`,
  артефакт — установщик `.exe`.
- `better-sqlite3` — нативный модуль, требует пересборки под целевую платформу;
  на windows-раннере это делает `electron-rebuild` автоматически, локально с Mac
  собрать Windows-версию не выйдет. Это причина, по которой релизы идут только через CI.
- Подпись кода не обязательна, но без неё SmartScreen покажет предупреждение при
  первом запуске.

## 15. Профили двух присланных прайсов

Оба файла — фармацевтические прайсы по Бишкеку, валюта KGS. Различаются во всём,
кроме этого.

| | **Неман-Фарм** `оптовый прайс 21.08.26.xlsx` | **Фармамир** `Прайс Фармамир от 18.08.26.xls` |
|---|---|---|
| Формат | xlsx (ZIP/OOXML) | xls (BIFF8, настоящий, не переименованный HTML) |
| Лист | `PRICE` | `TDSheet` — сигнатура выгрузки из 1С |
| Размер | 5930 строк × 11 колонок | 2726 строк × 11 колонок |
| Преамбула | **262 строки**, 312 merged-ячеек, 3 акционные таблицы-ловушки | 13 строк, merged нет |
| Строка заголовка | **263** | **14** |
| Данные | 265–5929, **5655 позиций** | 16–2726, **2703 позиции** |
| Категорий | 11, простым текстом | 9, вида `N. Название` |
| Цена | колонка F `Оптовые`, **число** | колонка E `Цена за ед.товара с НДС`, **текст** `1417,92` |
| № п/п | число | **текст** `2 700` (пробел в разрядах) |
| Артикул | **нет** | **нет** |
| Ед. изм. | `уп` (5653 из 5655) | `упак`/`уп`/`шт`/`флак`/`пл`/`туб`/`ампула` |
| Производитель | страна: `Индия`, `США` | завод: `SOLGAR/США`, `Psychotropics India` |
| Срок годности | `12-27` (ММ-ГГ) | `30.09.2028` (ДД.ММ.ГГГГ, текстом) |
| Прочее | `НДС` (12%/пусто), `Акция` (текст со скидкой и датами), `К.во в упак.` | `Нет скидки`, `Без НДС`, `Заводская упаковка` |

Практические следствия:

- **Парсер срока годности нужен на два формата** — и оба приводить к «конец месяца».
  `Ср.год. = 0` у Неман-Фарм означает «не применимо» (хозтовары), а не «просрочено».
- **Единицы измерения нормализуются по словарю**: `упак`/`уп`/`упаковка` → `уп`.
  Без этого сравнение цен между поставщиками будет сравнивать штуку с упаковкой.
- **Колонка `Акция` у Неман-Фарм** содержит готовый текст вида
  `Скидка: - 20% (10.08.2026-30.09.2026)`. Парсится regex'ом в процент + период —
  и тогда в сравнении цен можно показывать цену со скидкой, если акция активна.
- **Валюта KGS у обоих**, объявлена текстом в преамбуле, а не колонкой. Пока
  хардкодим в профиле поставщика; мультивалютность не нужна.

Эти два профиля — хороший тестовый набор: если импорт справляется с ними обоими
без ручной правки кода, он справится с большинством прайсов этого рынка.
Разумно завести их как фикстуры в тестах с самого начала.

## 16. Решённые и открытые вопросы

Решено:

- **Валюта** — только KGS, мультивалютность не нужна. Хардкодится в профиле поставщика.
- **Импорт** — автоматический из наблюдаемой папки, с ручным добавлением как
  запасным путём и очередью для файлов, чей профиль не опознан (§9).
- **Цены** — показываем и как в прайсе, и с учётом акций, рядом (§10).
- **Число поставщиков** — заранее неизвестно, и это нормально: архитектура
  к нему нечувствительна. Два прайса дают 8.3k позиций; SQLite с FTS5 держит
  миллионы строк, а узкое место (очередь подтверждения склеек) уже сделано ленивым.
  Единственное, что растёт линейно с числом поставщиков — разовая настройка
  профиля для каждого нового формата.

Открыто:

- **Смена правил нормализации обнуляет ключи позиций.** `item_key` считается от
  `name_norm`, поэтому правка `normalizeName` делает старые позиции
  неопознаваемыми: переимпорт создаёт новые записи, а прежние гаснут вместе с
  историей цен. Это уже наблюдалось при добавлении склейки числа с единицей —
  66 позиций из 8358 разъехались. Пока прайсов немного, лечится полной
  пересборкой базы; если правила придётся менять на живых данных, понадобится
  миграция, переносящая историю по старому и новому ключу.

- **НДС у Неман-Фарм**: колонка `НДС` = `12%` у 5105 позиций — включён ли он в
  колонку `Оптовые` или начисляется сверх? Из файла не выводится, нужно
  спросить поставщика. До ответа обе цены показываются как есть; в профиле
  заведён флаг `price_includes_vat`, переключение — одна настройка.
- **Папка наблюдения**: одна общая на всех поставщиков или своя на каждого?
  Общая проще и при опознании по сигнатуре достаточна — предлагаю начать с неё.
- Нужен ли экспорт истории цен (динамика за период) отдельным отчётом, или
  достаточно графика в карточке товара.
